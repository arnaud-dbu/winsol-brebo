{{# Track bleeds outside `.container` at every width (Figma 451:2902 desktop, 451:3272 mobile) via `bleed="true"` on the shared `slider` partial: it applies the `slider-bleed` utility (resources/css/base/spacing.css), which pulls the box out to the viewport edge with a negative margin and immediately re-adds that distance as padding — the box reaches the viewport edge but its content still starts at the same x as the container. That margin is derived from `50vw` minus the container's own half-width, so it also cancels the auto margin `.container` gains above its `max-width` — the bleed is full-width on the largest screens too, not just up to 1536px. `.slider` still clips with `overflow-x: hidden` (resources/css/components/slider.css, base rule), so the oversized swiper track is cut off exactly at the viewport edge; `.section` adds `overflow-x: clip` (resources/css/base/section.css) so the few pixels of scrollbar overshoot in `100vw` can never widen `document.documentElement` either. Header is left-aligned (no centring args) at both breakpoints. On desktop (451:2910) the slider's prev/next buttons sit beside the heading, right of the header row and aligned with its bottom edge; on mobile (451:3283) there is no nav at all, only pagination dots below the row. The dots are a deliberate departure from Figma in one direction only: they stay visible at *every* width, desktop included, where they sit under the track alongside the nav beside the heading — so nothing hides `.swiper-pagination` per breakpoint, and it shouldn't be "corrected" to mobile-only later. Keeping them visible is what `.slider-frame` in the shared partial is for: inside `.slider` they fell outside the clipped box. Both `navigation="true"` and `pagination="true"` are passed to the slider — the *placement* is handled entirely by the `[data-section='image_gallery']` rules in resources/css/components/slider.css, which reuse (and generalise) the `ranges` section's existing desktop-nav-beside-heading treatment and additionally hide `.slider__nav` below `lg` for this section. The `sectionHeader` partial is untouched; the `slider` partial only gained the neutral `.slider-shell` wrapper those rules flatten with `display: contents`, which changes nothing for the sections that don't opt into this treatment. `per_view="1.15,lg:1.4"`: at the base tier the design (451:3272, 402px wide mobile frame) shows one ~339px slide filling ~84% of the frame (339/402), i.e. slidesPerView ≈ 1/0.84 ≈ 1.15 — the same value already used by `ranges`/`projects`. From `lg` up the container's own padding is constant (`container` is `px-10` from `lg` through `4xl`), so the 1744px desktop frame (451:2902) is representative of the whole `lg+` range: a 1225px slide fills ~70% of the 1744px frame (1225/1744), i.e. slidesPerView ≈ 1/0.70 ≈ 1.4 — not the different value a plain per-breakpoint guess might suggest. `centered="true" loop="true"`: the active image sits in the middle of the bled track rather than flush against the container's left edge, so the peek of the neighbouring slide is symmetrical. Those two args are a pair — see the comment above the Swiper options in resources/js/components/sliders.js: centring alone would still collapse the peek to one side on the first and last slide, since Swiper cannot scroll past either end; only with `loop` is the composition identical at every position. Nothing about the bleed changes — Swiper measures its track from the element's content box, which `slider-bleed`'s padding keeps exactly container-wide, so the centred slide is centred on the container (and thus on the page) while the overflowing neighbours still get clipped at the viewport edge. #}}
